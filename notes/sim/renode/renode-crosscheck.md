# Renode cross-check: AM32 ramp limiter under a 250 Hz throttle sine

Date: 2026-10-26. This is the Renode (emulated MCU) side of the ramp-limiter
study. The main study runs in the native AM32 SITL. In this run the real ARM
firmware binary runs on an emulated AT32F421 / STM32L431 and drives the same
motor-physics code the SITL uses.

## TL;DR

* **No desyncs in any sine segment, in any variant, on either MCU.** Not with
  ±200 or ±600 DShot at 250 Hz around 1047, and not with ramp 16, 64 or 255.
  The only `desync_happened` increments came at the final cut to zero
  throttle while the motor was still spinning at about 14k RPM.
* **The stock ramp limit (16 per 50 µs tick, which is 320 000 duty-units/s) is
  just enough for ±200 at 250 Hz.** That swing needs 2π·250·196 ≈ 308 000/s.
  The applied duty swing is 391 p-p against 400 commanded. **It cuts ±600 down
  to a triangle:** 518 p-p fundamental against about 1176 needed, a 735–1343
  range, and about 55° of extra phase lag.
* **ramp 64 and ramp 255 give the same result**: the full ±600 is applied
  (1174–1176 p-p, slew of about 950 000/s, which is under 64×20 kHz). So 64 is
  already enough for ±30 % at 250 Hz. Ramp-limited tracking also gives a
  **timing-sensitive DC duty offset**: +19 duty units at a 20 µs physics batch
  and −21 at a 2 µs batch. That moves mean RPM by ±300 to 400. It would show up
  as a collective (thrust) shift caused by cyclic input.
* Mean bus current (firmware `actual_current`) is 7.6 A steady at 1047. With
  ±600 it rises to 10.1 A on stock and 17.8 A on ramp 64/255.
* RPM ripple at 250 Hz is small, because inertia filters it: about 114 RPM p-p
  for ±200, and 337 RPM p-p for ±600 when not limited. The mean is about
  13.9k RPM at DShot 1047 with this model.
* The CAN build cannot start this motor unless it has a valid DroneCAN node id.
  Fred's `esc1_config.bin` has 0xFD in every CAN byte. See Blockers.

## How Renode is coupled to the motor and to DShot (comparability with the SITL)

**Motor physics.** A Renode peripheral, `AM32_F051_Bridge.cs`, loads
`~/am32/ESCSim/build/native/libam32sim.so`. That library is built from
`ESCSim/native/am32sim/src/{motor.c, sitl_config.c, am32sim_shim.c}`, and its
`motor.c` is a copy of AM32's `Mcu/SITL/sim/motor.c` with small changes:

* it keeps the electrical angle as its own wrapped accumulator (`theta_e`)
  instead of computing `theta*pole_pairs` each step;
* it drops the scope/BEMF capture helpers.

Physics substeps are 500 ns, the same `physics_dt_ns` default as the SITL. The
difference is how the firmware and the physics exchange data:

* Every **20 µs of virtual time** (the bridge `batchUs`, which ESCSim
  hard-codes) the bridge does three things:
  * reads the half-bridge state from the emulated GPIO MODER/ODR/AF and TIM1
    ARR/CCR/dead-time registers;
  * reads which phase COMP is sensing;
  * advances the physics to "now". Inside the batch, the PWM edges are
    reconstructed from the timer counter.
* Comparator transitions produced during the batch are replayed into the
  emulated COMP output, but **all of them at the end of the batch**. So a zero
  crossing reaches the firmware's EXTI with up to 20 µs of extra latency. At
  14k RPM and 7 pole pairs that is about 12° electrical, against a 102 µs
  commutation step.
* The SITL instead runs the firmware natively against the same motor.c, with
  its own timing scheme (see ESCSim `SITL/TIMING-DESIGN.md`).

I ran the F421 variants a second time with the batch set to 2 µs, using
`gen_batch_wrapper.py`, which patches the generated platform without editing
ESCSim. The effect is about 0.4 % on steady RPM, and 12 % less RPM ripple at
±200 (114→100 RPM p-p). Desync behaviour did not change: there were none
either way. The DC offset in the ramp-limited case changed sign.

**DShot.** `AM32ThrottleGenerator.cs` produces real DShot300 pin edges in
virtual time. They go into the emulated TIM15 input-capture and DMA path, and
the firmware's own `computeDshotDMA()` decodes them. Nothing is injected
already decoded. We set its `DshotValue` property before every 100 µs step.
Its `DshotFrameUs` property sets the frame rate. The firmware decoded 9 999
frames/s with no errors.

**Readback.** Between steps, firmware globals are read straight from emulated
SRAM at their ELF symbol addresses. The motor's true mechanical RPM and phase
currents come from the bridge. Sampling happens while the emulation is paused
at an arbitrary instruction, so a variable can be caught mid-update. For
example, `duty_cycle` briefly holds the unclamped setpoint inside
`tenKhzRoutine()`. For that reason the analysis uses `last_duty_cycle`, the
committed post-ramp duty on a 0–2000 scale.

**Phase convention.** The 250 Hz fit has about 9° of duty lag even when the
ramp is not limiting. That is 100 µs, one sample: the command is set at the
start of a step, the frame goes out during the step, and the sample is taken
at its end. It is measurement latency, not ESC lag.

relative to the commanded sine. `desyncs` is the increase of
`desync_happened` over the whole segment. The full columns are in `summary.csv`.

the ISR phase drifts. The p99 of 320 000/s, which is exactly 16 × 20 kHz,
confirms the stock limiter is active. ±200 on ramp 64/255 is identical to
stock, because it is never limited.

Desyncs outside the sine segments: when throttle is cut from about 14k RPM to
0 at the end, F421 ramp255 (batch 20 µs) logged 2 and L431 CAN ramp64 logged 1.
In those cases the firmware stops driving and the motor coasts down. During
startup on the ramp segment, every run logged 1 desync and a few bemf timeouts.
That is AM32's normal open-loop startup handover; the same thing happens with
ESCSim's stock models.

Other observations:

* **The DC offset when ramp-limited depends on micro-timing.** I checked mean
  `last_duty_cycle` over 0.1 s windows of the ±600 segment. It settles within
  about 0.2 s to 1039 (20 µs batch, both MCUs) or 997 (2 µs batch), then stays
  there. The limited tracker has a weakly determined offset, and the emulated
  ISR phase decides which way it goes. In flight, that means cyclic input
  above the ramp limit can produce a few percent of collective error, with a
  sign that cannot be predicted. ramp 64/255 removes it: the mean stays at
  1018.
* With full ±600 tracking, mean RPM falls about 210 RPM (1.5 %) because the
  prop load is nonlinear (∝ω²). Mean bus current (firmware `actual_current`)
  goes from 7.6 A steady to 8.7 A at ±200 and 17.8 A at ±600 (10.1 A on
  stock, where the limiter cuts the swing).
* The F421 and L431 results agree to within about 2 % on RPM and 7 % on RPM
  ripple. They agree exactly on duty, because it is the same ramp logic.

## Blockers / caveats

1. **The CAN build needs a valid node id, or the motor never starts (emulation
   finding).** `esc1_config.bin` bytes 176–183 are all 0xFD, so can_node is
   253. `canardSetLocalNodeID` rejects anything above 127. The node then stays
   anonymous, and `DroneCAN_update()` keeps running dynamic node allocation.
   In that state the emulated VIMDRONES_L431_CAN never gets this motor out of
   startup:
   * duty stays capped at 440;
   * `zero_crosses` stays at 14 or below;
   * after 10 bemf timeouts, stuck-rotor protection latches.

   I got the same failure with node 0 (explicit DNA) and with the bxCAN
   connected to a loopback multicast bus that had no allocator. The same
   firmware with node 11 starts and runs normally. VIMDRONES_L431 (non-CAN,
   same hardware) and NEUTRON_L431 both start the Hakea motor with Fred's
   file. With DNA pending, the low-KV `vimdrones_nano_2216` model still
   starts, but `racer_5inch` does not. I have not checked whether a real CAN
   ESC behaves the same way. Fred's F421 is not a CAN ESC, so this does not
   affect his hardware. If a CAN ESC is ever used, set a node id. Evidence is
   in `diagnostics/`.
2. **DroneCAN RawCommand stimulus was not done.** ESCSim bridges the emulated
   bxCAN to the SITL's UDP multicast bus in host wall-clock time. Renode runs
   at about 0.35× real time, so a 250 Hz command stream sent from the host
   would reach the firmware at about 90 Hz of virtual time, with jitter. Doing
   this properly needs a CAN frame source scheduled inside Renode in virtual
   time, like the throttle generator. ESCSim does not provide one.
3. **The physics exchange granularity is 20 µs** (see above). The 2 µs check
   shows that conclusions about duty and desync do not depend on it. RPM
   ripple amplitude moves by about 12 %, and the sign of the ramp-limited DC
   offset changed.
4. I used my own gcc 10.2.1, not AM32's pinned xpack 10.3.1. The ELF is linked
   at 0x08001000 with no bootloader loaded (ESCSim's no-bootloader mode, which
   uses the same start address as AM32's vector table offset).
   `delayMillis` is skipped by ESCSim's hook while interrupts are masked
   (startup tune only).
5. I did not edit ESCSim or AM32. Nothing I found needs fixing in ESCSim,
   apart from points 2–3 as possible features. One note for ESCSim: the
   `--batch-us` value is not configurable from the CLI.

## Reproduce

```sh
cd ~/vehicles/hakea
# once: worktree + patch (already done)
git -C am32-hakea worktree add ~/vehicles/hakea/am32-renode -b sim/renode-check
git -C am32-renode apply ~/vehicles/hakea/scripts/sim/ramp-study.patch
# build the 6 variants into am32-renode/variants/
scripts/sim/renode/build_variants.sh
# all 6 runs (~2 min) + summary
scripts/sim/renode/run_all.sh
# a single run, e.g. with the 2 us physics batch
source ~/venv-ardupilot/bin/activate
python scripts/sim/renode/run_crosscheck.py FOXEER_F421 \
    am32-renode/variants/FOXEER_F421_ramp255.elf --name FOXEER_F421_ramp255_batch2us --batch-us 2
python scripts/sim/renode/analyze.py
```

The Renode monitor uses TCP 34571 (`--monitor-port`). No UDP ports are opened,
because CAN is left unconnected (`--can-bus -1`).

## Files

* `scripts/sim/renode/`
  * `build_variants.sh`: builds the firmware variants.
  * `run_crosscheck.py`: one run (launches Renode, drives the stimulus, logs).
  * `hakea_stim.py`: runs inside Renode's IronPython; does the virtual-time
    stepping and sampling.
  * `renode_monitor.py`: telnet monitor client.
  * `analyze.py`: produces `summary.csv` and the table.
  * `run_all.sh`: the full batch.
  * `gen_batch_wrapper.py`: physics-batch override.
  * `eeprom/esc1_config_can11.bin` and `eeprom/esc1_config_can0.bin`: the
    patched EEPROM images.
  * `work/<run>/`: the generated .repl/.resc and the Renode log for each run.
    It is git-ignored.
* `notes/sim/renode/`
  * `raw/<run>.csv` and `raw/<run>.json`: 100 µs samples and run metadata,
    including segments, the model JSON and the EEPROM readback.
  * `summary.csv`: per-segment metrics.
  * `model_used.json`.
  * `diagnostics/`: trial summaries for the CAN node-id issue.
